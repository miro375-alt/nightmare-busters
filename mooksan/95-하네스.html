봇은 재미를 못 잰다. 봇이 거르는 것은 고장 · 밸런스 · 페이싱이다.

「걷기만 하고 아무 일도 안 일어나는 시간」이 길면 재미없다는 지적은 측정 가능한 결함이다.

1. ★ 제1원칙 — 시뮬레이터를 따로 만들지 않는다

2026-07-31에 실제로 저지른 실수:

밸런스 검증용 sim.js를 게임 로직을 다시 구현해서 만들었다.

그러면 게임을 고칠 때마다 시뮬도 같이 고쳐야 하고, 어긋나는 순간 검증이 거짓말이 된다.

하네스는 반드시 실제 게임 코드를 구동한다. 방법은 게임에 틱을 분리한 헤드리스 모드를 넣는 것이다.

// 게임이 노출해야 하는 계약
window.__H = {
  reset(seed),          // 시드 고정 초기화
  tick(n),              // rAF 없이 n프레임 진행 (수천 프레임을 수 ms에)
  input(keys),          // {up,down,left,right,ok,note,run} 상태 주입
  state(),              // 직렬화된 전체 상태
  events(),             // 이벤트 로그 배열
  chapter(n),           // 특정 챕터로 점프 (부분 검증용)
};

tick()이 있으면 브라우저 한 탭에서 수백 판을 몇 초에 돌린다. 그리고 그건 진짜 게임 코드다.

2. 게임에 먼저 넣어야 할 구조

하네스 요구사항 = 어차피 필요한 리팩터링이다. → [[99-작업]] C항

필요 구조왜
시드 RNG (Math.random 전량 제거)같은 시드 = 같은 판. 실패를 재현해야 고친다
틱 분리 (loop에서 update(dt) 떼어내기)rAF 없이 돌려야 빠르다
상태 직렬화 (state() / load())지표 수집 · 세이브 · 특정 상황 재현
이벤트 로그{t, type, payload} — 이동·조사·경고·편입·사망·아이템
맵 데이터 분리 (maps/*.json)챕터 점프 · 맵만 바꿔 A/B

★ 시드 RNG가 가장 먼저다. Math.random()이 엔티티 배치·순찰 경로·연출에 쓰이는데, 재현이 안 되면 버그를 두 번 볼 수 없다.

3. 봇 3종

봇행동잡아내는 것
원숭이완전 무작위 입력크래시 · 소프트락 · 상태 꼬임
규칙봇[[62-공략]]의 권장 진행을 그대로 수행정상 경로가 실제로 통하는가
탐욕봇최대 깊이 · 최대 수집 · 위험 감수밸런스 상한. 「깨지는 조합」 탐색
  • 세 봇을 시드 100개씩 돌린다. 브라우저 한 탭에서 수십 초
  • 규칙봇 클리어율이 95% 미만이면 그 챕터는 불공정하다
  • 원숭이가 소프트락에 걸리면 그 시드를 케이스로 박제한다

4. 지표와 기준선

harness/baseline.json에 통과한 값을 저장하고, 새 변경이 이를 악화시키면 차단한다.

지표기준벗어나면
규칙봇 클리어율≥ 95%불공정
원숭이 소프트락0건진행 불가 버그
챕터 소요 시간4~9분짧으면 허전, 길면 늘어짐
무행동 구간 최대치≤ 25초★ 지루함
선택 빈도 (분당 의미 있는 결정)≥ 3회★ 사무 노동
사망 원인 분포 (편입 / 봉인 / 안전지대 상실)어느 하나 ≥ 70% 금지한 가지 압박만 작동 중
경고 → 사망 리드타임≥ 1.5초예고 없는 죽음
안전지대 복귀 간격40~120초너무 잦으면 지루, 드물면 무의미
프레임당 그리기 호출기준선 ±20%렌더 회귀

「무행동 구간」 정의 — 이벤트 로그에서 이동 외의 이벤트가 하나도 없는 최장 구간. 걷기만 하고 아무 일도 안 일어난 시간이다.

「선택」 정의 — 되돌릴 수 없고, 결과가 갈리는 입력. 조사 · 안전지대 이탈 · 조력자 지시 수용/거부 · 아이템 사용. 단순 이동은 선택이 아니다.

5. 시각 회귀

harness/shots.json   →  상황 목록 (챕터 × 상태)
harness/shots/       →  기준 스크린샷
harness/shots_new/   →  이번 회차
  1. 각 상황을 __H로 세팅 → 브라우저에서 캡처
  2. 기준과 픽셀 diff. 임계값 초과 항목만 표시
  3. 판단은 사람이 한다. diff는 「달라졌다」만 말하지 「나빠졌다」를 말하지 않는다

철칙 — 목업으로 검수하지 않는다. 실제 빌드 스크린샷만 쓴다.

캡처 목록(초안): 챕터별 ①진입 ②안전지대 안 ③엔티티 조우 ④경고 발생 ⑤아이템 획득 ⑥대화창 ⑦안전지대 만료 임박 ⑧사망 화면 → 6챕터 × 8 = 48장

6. 루프 절차

① 실행     harness/run.mjs  →  봇 3종 × 시드 100 + 스크린샷 48장
② 판정     기준선 대비 벗어난 항목만 목록화
③ 분류     [고장] → 즉시 수정
           [밸런스·페이싱] → 수치 조정 1건
           [판단 필요] → 사람에게 올린다
④ 수정     ★ 한 번에 하나만 바꾼다
⑤ 재실행   개선됐는가 · 다른 지표가 나빠지지 않았는가
⑥ 확정     좋아졌으면 커밋 + 기준선 갱신 / 아니면 롤백
⑦ 반복

★ 한 턴에 하나만 바꾼다

여러 개를 동시에 고치면 무엇이 효과였는지 알 수 없다. 루프의 가치는 속도가 아니라 인과를 붙잡는 것이다.

사람에게 올리는 것

  • 지표는 통과했는데 화면이 이상한 것
  • 밸런스는 맞는데 이야기가 안 맞는 것
  • 봇이 클리어했는데 경로가 의도와 다른 것 ← 종종 제일 중요하다
  • 기준선 자체를 고쳐야 할 것 같은 때

7. 실패 케이스 박제

harness/cases/
  0031_softlock_ch2_mobile-rack.json   { seed, chapter, inputs[], 기대, 실제 }
  • 발견된 버그는 시드 + 입력 시퀀스로 저장
  • 이후 모든 회차에서 자동 재생 → 같은 버그가 두 번 나오지 않는다
  • 케이스가 쌓이면 그게 회귀 테스트 묶음이 된다

8. 도입 순서

지금 구현된 것은 구버전 규칙의 1챕터뿐이고 곧 교체된다. 하네스를 지금 코드에 맞춰 짓는 것은 낭비다. 순서는 이렇다.

단계내용선행
0시드 RNG · 틱 분리 · 상태 직렬화 · 이벤트 로그—
1__H 계약 노출 + harness/run.mjs 골격0
2원숭이봇 + 소프트락 탐지1
3챕터 1을 새 규격(목표·아이템·안전지대·엔티티)으로 재구현[[60-레벨]]
4규칙봇 + 지표 수집 + 기준선 확정2·3
5스크린샷 회귀3
6탐욕봇 + 케이스 박제4
7챕터 2~6 확장 — 각 챕터는 하네스를 통과해야 다음으로 넘어간다4·5

★ 0단계가 진짜 시작점이다. 그리고 0단계는 어차피 해야 할 리팩터링이다.

9. 반복 실행 방식

방식언제
수동 — 변경 후 run.mjs 한 번기본. 인과가 가장 선명하다
/loop — 스스로 페이스를 잡아 반복밸런스 수치 탐색처럼 같은 작업을 여러 번 돌릴 때
예약 실행챕터가 여러 개 쌓여 전체 회차가 길어졌을 때

주의 — 루프를 오래 돌리면 지표는 좋아지는데 게임은 재미없어질 수 있다. 기준선은 목표가 아니라 하한선이다. 주기적으로 사람이 직접 플레이해야 한다.

10. 이번 세션에서 얻은 교훈 (하네스가 있었으면 잡았을 것)
